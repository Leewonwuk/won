# Claude 광역 규약 (전 프로젝트 공통)

작업 도메인(코드·트레이딩·게임 등)에 무관하게 모든 프로젝트에 적용되는 협업 규약입니다.
프로젝트별 세부 규약은 별도 문서로 관리하고, 본 문서는 광역 원칙만 다룹니다.

---

## 1. 거인의 어깨 (Giants' Shoulders) — 최우선 규약

**원칙:** 모든 프로젝트에 분야 거장 5명의 검증된 원칙 체크리스트를 적용해 설계·구현·리뷰 단계에서 평가한다.

### 5단계 절차
1. 프로젝트의 장르/도메인 명확화
2. 해당 분야 거장 5명 제안 → 사용자 승인
3. 각 거장의 대표 원칙 2-4개 추출 → 체크리스트화 (총 10-20 항목)
4. `docs/GIANTS_SHOULDERS.md`(또는 프로젝트 루트)에 체크리스트 저장·참조
5. Phase/Milestone 단위로 결과물을 체크리스트에 비춰 점수·코멘트

### 병렬 에이전트 구성 규약
- 검증 에이전트를 돌릴 때 **"거인의 어깨 평가자" 슬롯 필수 포함**. 생략 금지.
- 기본 병렬 슬롯: ①버그 헌터 ②코드 품질/고도화 ③GA 스모크 테스트 ④**거인의 어깨 평가자(필수)**
- 거장 미선정 단계라면 평가자가 "5명 후보 + 1차 체크리스트 초안" 산출

### Pre-Mortem (실패 관점 역분석) 필수
- 매 Phase 평가 시 "어떻게 하면 이게 실패하게 되는가?" 관점 역분석
- 각 거장 원칙별로 **Failure Mode 1-2개** 도출 (실패 시 증상 + 유발 조건)
- 현 결과물이 해당 실패 모드에 **근접/도달**했는지 점검
- 리포트 구조에 "Failure Mode" 섹션 필수

**Why:** 긍정 체크리스트만으로는 맹점이 남는다 (멍거의 inversion / Kahneman pre-mortem). 실패 경로를 먼저 그려보면 숨은 제약이 드러난다. 외부 기준 없이 주관 평가만으로는 품질 담보 어렵다.

## 2. GitHub 업로드 보호 규칙

**원칙:** `git push` / force push 전 원격 저장소 현황을 반드시 확인하고, 명시 요청받은 파일 외에는 절대 건드리지 않는다.

### How to apply
- push 전 항상 `gh repo view` 또는 `git fetch && git log origin/branch` 로 원격 현황 확인
- force push (`--force`, `--force-with-lease`) 는 사용자가 **명시적으로 요청한 경우에만** 실행, 반드시 사전 경고
- 새 파일 업로드 시 기존 원격 파일 목록을 먼저 보여주고 사용자 확인을 받은 뒤 진행
- 요청받은 특정 디렉토리/파일만 추가, **나머지 원격 파일에는 절대 손대지 않음**

**Why:** 과거 force push 로 사용자의 중요한 포트폴리오 PDF (면접 준비 자료) 가 전부 삭제된 사고 발생. 백업이 없어 GitHub API 로 간신히 복구.

## 3. 대규모 수정·검증은 멀티 에이전트 하네스 사용

**원칙:** 수정 범위가 넓거나 검증 시나리오가 많을 때는 단일 에이전트 순차 처리 대신 멀티 에이전트 워크플로로 전환한다.

### 트리거 조건
- 파일 **3~4개 이상** 동시 수정
- 시스템 재설계 단계
- 백테스트/검증 시나리오 **다수 동시 실행** 필요

### How to apply
- 트리거 조건 만족 시 Architect → Builder → Reviewer 역할 분담 워크플로로 전환
- 단순 버그 1~2개 수정은 단일 처리 OK
- 단일 에이전트 순차 처리는 컨텍스트가 빨리 차서 중간에 놓치는 수정이 생긴다

**Why:** 단일 에이전트는 컨텍스트 한계로 큰 변경에서 누락 발생. 하네스는 역할 분담으로 병렬·재검증이 안전하고 결과 비교가 쉽다.

## 4. 기억 요청 즉시 저장 규칙

**원칙:** 사용자가 "기억해줘" 또는 유사 표현을 쓰면 즉시 메모리 파일에 저장한다.

### How to apply
- 요청 즉시 적절한 type (user/feedback/project/reference) 으로 분류
- 메모리 파일 저장 + 인덱스 파일 (예: `MEMORY.md`) 업데이트
- **절대 잊거나 나중으로 미루지 않는다**

**Why:** 세션이 끊겨도 다음 Claude 인스턴스가 컨텍스트를 이어받을 수 있도록.

## 5. 의사결정 보고 시 "풀이 습관"

**원칙:** 보정 제안·검증 결과 요약·재설계 옵션 제시 등 사용자의 판단을 청하는 모든 국면에서 축약어·기술 용어로만 보고하지 않는다.

### 적용 범위 (모든 의사결정 청취 국면)
- 보정·수정 제안
- 검증 에이전트 리포트 요약 (Bug Hunter / GA Smoke / 거인의 어깨 / 정합성 등)
- 재설계·범위 분할 옵션 제시 (A/B/C)
- Phase 완료·진입 보고

### 3요소 포맷 (항목마다)
1. **구체 시나리오** — 사용자가 실제로 겪을 한 장면
2. **사용자 체감** — 그 순간 어떤 느낌인지 1줄
3. **수정 이유 / 판정 근거** — 고치지 않으면 어디서 신뢰·리듬·재미·신뢰성이 깨지는가

### 용어 치환 규칙
- 축약어 (C1, H-3, P0 등) 대신 평문
- 기술 용어 (payload, null 경로, emit, scope, Chebyshev 등) 대신 일상어
- 예: "C1 편의시설 이용 흐름 미구현" → "지금 게임에서 환자가 해우소·국밥집 같은 편의시설에 들어가는 동작 자체가 아직 없음"
- 예: "payload" → "이벤트에 함께 실어 보내는 정보"
- 비유가 도움 될 땐 적극 사용

### A/B/C 옵션 제시 시
- 각각 **지금 드는 시간 · 나중 감당할 비용** 을 구체 분 단위 또는 "이 Phase 끝나고 또 손대야 함" 식으로 표기

### 허용 범위
- 축약어 표기는 **체크리스트 진행 로그·백로그·코드 주석에서만** 허용
- **사용자에게 의사결정을 청할 땐 절대 금지**

**Why:** 사용자가 비코드 기획 관점으로 작업물을 본다. 축약어·기술 용어로만 요약하면 의사결정 불가. 과거 검증 결과를 'CRITICAL 4건 / 축2 2/5' 식 축약으로만 보고했다가 반려당한 사건이 계기.

## 6. 과거 코드/버전 단정 시 grep만으로 결론 금지

**원칙:** 사용자가 "이전 버전에 X 기능 있었지?" 류로 물을 때, 현재 파일시스템 grep 결과만으로 "없었다"고 단정하지 않는다.

### How to apply
1. grep 결과로 "없다" 판단되면 먼저 `docs/`·`ADR.md`·`PRD.md`·과거 버전 디렉토리·기획 문서·백로그 추가 확인
2. `git log --all --oneline -- path/` + `git show <sha>` 로 과거 히스토리 확인 (삭제·리팩터된 기능일 수 있음)
3. 모든 체크 후에도 증거가 없으면 **"현재 트리와 문서에서는 확인 안 됨. 사용자 기억이 맞다면 구현해드리겠습니다"** 로 완곡 보고
4. 사용자가 "실제로 있었다"고 재확인하면 논쟁하지 말고 즉시 구현으로 전환

**Why:** 사용자 기억과 grep 결과가 충돌할 때 "grep이 이겼다"고 가정하는 것은 사용자를 무시하는 응답. 코드는 리팩터·삭제되지만 사용자 기억은 사실일 수 있다.

## 부록 — 체크리스트 진행 리듬 (적용 시 권장)

큰 체크리스트나 다단계 작업에서 권장되는 협업 리듬:

1. 한 번에 다 처리하지 말고 **3개씩 묶어** 진행
2. 각 묶음마다: ①기존 시스템이 요구를 만족하는지 **검증** → ②없으면 **새로 구현** → ③모호하거나 결정해야 할 부분은 **사용자에게 확인** (혼자 판단 금지) → ④사용자 승인 후 다음 묶음
3. 완료 시 체크리스트 `[ ]` → `[x]` 업데이트
4. 매 묶음 후 **병렬 4종 검증 에이전트** 실행 (위 §1 참조)

**Why:** 큰 배치를 한 번에 구현하면 로직 오류·방향 어긋남이 누적된다. 외부 기준(거장 체크리스트) 없으면 품질 담보 어렵다.
